## 概要

親Issue: https://github.com/FutureLinkNetwork/mypl_laravel3/issues/1955

画像変換処理（リサイズや回転など）が画質に与える劣化度合いを調査し、現在適用されている画像処理ライブラリ（ImageMagick）のパラメータ設定見直しや、不要な強制変換の排除、必要に応じたライブラリの置き換えを検討します。

Issue で挙げている必要なタスクは次の4つです。

- **画像加工プログラムの調査**: 画像配信における現状のプログラム構成を調査し、PNG画像が意図せずJPEGに変換される等の不要な加工が発生していないか確認する。
- **データ放送以外のPNG形式維持の実装**: データ放送用途の画像を除き、元がPNG形式の画像は強制的なJPEG変換を行わずにPNGのまま返却するようにする。
- **設定仕様の調査**: 現在適用されているImageMagickのパラメータ設定および画質に関する仕様を調査する。
- **画像劣化調査とライブラリ検討**: 画像変換処理（リサイズや回転）が画質に与える影響を調査し、必要に応じて別の画像処理ライブラリへの置き換えを検討する。

## やったこと

- **画質劣化の箇所調査（2026-09-29、FLNYoshidaRyuta）**: 各リポジトリのコード読解による推測であり、実画像の比較・計測は未実施。調査対象コミットは mypl_pro `main` の `2f3c0da`、089_ImageServer `main` の `5d10769`、056_img2.mypl.net `main` の `a02499b`。
- **結論の要約**: 劣化が大きいと見込まれる箇所は、(1) 089_ImageServer で長辺 2000px 超を GD 縮小・品質未指定 JPEG（既定約75）、PNG は大きさに関係なく JPEG 変換、(2) 056_img2 で要求サイズ超を ImageMagick 縮小・品質82・4:2:0・ICC 削除の JPEG、(3) pro の再編集で img2 の `s=1000_1000` 配信画像を元にトリミング等し再アップロードして劣化が積み重なる。pro そのままアップロード・8MB以下・長辺3000px以下・EXIF向きなし JPEG・長辺2000px以下かつ表示サイズ以内の場合は S3 から img2 出力まで再エンコードが入らない条件がある。
- **配信経路と処理系**: 表示 URL は `//img2.mypl.net/image.php?id={ファイル名}&p=s3-img-origin01&s=1000_1000` 形式。img2 は `http://image.mypl.net/{p}/{id}.nolimit` 経由で ImageServer が S3 から取得。段ごとの再エンコード条件は pro フロント（canvas/Cropper/heic2any 等）、pro サーバー（GD・EXIF向き JPEG）、S3（なし）、089_ImageServer（GD・長辺2000px超または PNG）、056_img2（ImageMagick・要求サイズ `s` 超）と整理されている。Issue 本文の ImageMagick は img2 のみで、ImageServer と pro サーバーは GD を使用。
