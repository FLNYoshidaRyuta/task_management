## 概要

初期設定の完了判定と保存内容を、担当者ごとの行から店舗に1件の設定へ変える。

同じ店舗を別の担当者が開いても、誰か1人が完了していれば初期設定の再表示はしない。保存し直しても担当者ごとの行は増やさない。複数行があってどれを店舗の設定にするか決められないときは、自動で上書きせず確認待ちにする。画面へ渡す値は、利用者が見る設定項目に限る。

OEMのユーザー認証と店舗の解決はそのままにする。まいぷれのユーザー解決へは合わせない。

初期設定の4項目（店舗理解、投稿目的、確認の仕方、言い方）は店舗共通の設定である。mypl_pro では完了判定が店舗IDと担当者IDの組み合わせだったため、別の担当者が同じ店舗を開くと未完了と判定され、初期設定が再び出ていた。生産でも、同じ店舗に複数行があり内容が違う例があった。そのため、最新行を無条件に正本にせず、判定できない行は確認待ちにしている。console-pro の `develop` は、`SetupProfileService` が今も `SHOP_ID` と `OWNER_USER_ID` の両方で完了判定と保存をしている。別担当者で再表示される状態が残っている。画面へ渡す設定から、利用者IDや監査用の日時を除く変更も mypl_pro にある。console-pro では、「あとで」の端末内抑制に今のログインユーザーを使っているため、その判定に必要な情報は残す。

対応する mypl_pro: https://github.com/FutureLinkNetwork/mypl_pro/issues/958 、https://github.com/FutureLinkNetwork/mypl_pro/pull/1073 。画面へ渡す項目の限定: コミット `64b4c12e` 。

## やったこと

2026-11-02 コメント「本番の `SHOP_SETUP_PROFILES` 重複調査」を実施した。

取得 SQL は `<setup_schema>` と `<oem_schema>` に `SHOP_SETUP_PROFILES` と `oem_user` があるスキーマ名を入れ、`SHOP_ID` が複数行ある店舗について `SHOP_SETUP_PROFILES` と `oem_user` を JOIN して `COMMITTED_AT` / `UPDATED_AT` 降順で並べた。

結果の概要: 重複がある店舗は6店舗・13レコード。`shop_user` の行が複数ある店舗は無かった。1店舗内の所有者 role の組み合わせは `shop_user` + `oem_customer_user`、`oem_customer_user` + `system_admin`、`system_admin` + `shop_user` + `oem_customer_user` の3種類。所有者が論理削除されている行（`deleted_at` あり）、所有者が見つからない行（`u.id` が NULL）は無かった。`COMMITTED_AT` と `UPDATED_AT` が両方 NULL の行は無かった。

## 残りのやること

- ユーザーAが完了した店舗を、行を持たないユーザーBが開いても、初期設定の再表示が出ない
- ホーム、ニュース、初期設定画面、設定画面、投稿準備が同じ店舗の設定を参照する
- 保存し直しても担当者ごとの新規行は増えない。最後に保存した人は既存の監査列に残る
- 複数行があり、どれを採用するか決められない店舗は、自動で上書きせず確認待ちにする
- 既存の複数行は、採用行と退避方法が追える形で整理する。整理後に店舗1行を保つ
- 画面へ渡す値から、利用者IDや監査日時を除く。「あとで」の端末内抑制に必要なログイン情報は残す
- OEMのユーザーと店舗の解決は変えない

改修前の再現手順: ユーザーAで店舗Xの初期設定を完了する → `SHOP_SETUP_PROFILES` に店舗XとユーザーAの組み合わせで行が保存される → 行を持たないユーザーBで店舗Xを開く → 未完了と判定され、初期設定の案内が再び出る。

テスト手順: ユーザーAが完了した店舗をユーザーBが開く結合テスト。保存し直しで担当者別の行が増えないテスト。複数行で採用先が決まらないとき、確認待ちになり自動保存しないテスト。ホームとニュースで、完了済み店舗に案内が出ないことを確認する。PHPUnit はコンテナ内で `APP_ENV=testing` を付けて実行する。
