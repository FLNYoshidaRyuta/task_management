## 概要

初期設定の完了判定と保存内容を、担当者ごとの行から店舗に1件の設定へ変える。同じ店舗を別担当者が開いても誰か1人が完了していれば初期設定の再表示はしない。保存し直しても担当者ごとの行は増やさない。複数行で採用先が決められないときは自動上書きせず確認待ちにする。画面へ渡す値は利用者が見る設定項目に限る。OEMのユーザー認証と店舗の解決はそのまま。まいぷれのユーザー解決へは合わせない。

初期設定4項目は店舗共通。mypl_pro では完了判定が店舗IDと担当者IDの組み合わせで、別担当者が同店舗を開くと未完了と判定され再表示されていた。生産でも同店舗に複数行で内容が違う例があり、最新行を無条件正本にせず判定不能行は確認待ちにしている。console-pro の `SetupProfileService` は `SHOP_ID` と `OWNER_USER_ID` の両方で完了判定・保存している。

対応する mypl_pro: https://github.com/FutureLinkNetwork/mypl_pro/issues/958 、https://github.com/FutureLinkNetwork/mypl_pro/pull/1073 。画面へ渡す項目の限定はコミット `64b4c12e` 。「あとで」の端末内抑制にログインユーザーを使うため、その判定に必要な情報は残す。

## やったこと

2026-11-02 コメント「本番の `SHOP_SETUP_PROFILES` 重複調査」を実施。`<setup_schema>` と `<oem_schema>` にスキーマ名を入れた SQL で重複店舗を取得した（コメント本文に SQL 記載）。

結果: 重複がある店舗は6店舗・13レコード。`shop_user` の行が複数ある店舗は無かった。1店舗内の所有者 role の組み合わせは `shop_user` + `oem_customer_user`、`oem_customer_user` + `system_admin`、`system_admin` + `shop_user` + `oem_customer_user` の3種類。所有者が論理削除されている行（`deleted_at` あり）、所有者が見つからない行（`u.id` が NULL）は無かった。`COMMITTED_AT` と `UPDATED_AT` が両方 NULL の行は無かった。

## 残りのやること

受け入れ条件: ユーザーAが完了した店舗を行を持たないユーザーBが開いても初期設定の再表示が出ない。ホーム・ニュース・初期設定・設定・投稿準備が同店舗設定を参照する。保存し直しても担当者別新規行は増えず、最後に保存した人は監査列に残る。複数行で採用先が決められない店舗は確認待ち。既存複数行は採用行と退避が追える形で整理し店舗1行を保つ。画面へ渡す値から利用者ID・監査日時を除き、「あとで」端末内抑制に必要なログイン情報は残す。OEMのユーザーと店舗解決は変えない。

改修前再現: ユーザーAで店舗X初期設定完了→`SHOP_SETUP_PROFILES` に店舗XとユーザーAの行→行を持たないユーザーBで店舗Xを開く→未完了と判定され案内が再出る。

テスト: ユーザーA完了店舗をユーザーBが開く結合、保存し直しで担当者別行が増えない、複数行で採用先不定時確認待ち・自動保存しない、ホームとニュースで完了済み店舗に案内が出ない。PHPUnit はコンテナ内 `APP_ENV=testing` で実行。
