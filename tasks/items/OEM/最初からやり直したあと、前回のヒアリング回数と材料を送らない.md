## 概要

ニュース作成のヒアリングで「最初からやり直す」を押したあと、次の送信に前回のヒアリング回数と材料が残らないようにする。ヒアリング状態を送るときは、回数も必ず対で送る。

mypl_pro では、やり直し後もブラウザに前回の `hearing_question_count` と `material_ledger` が残り、サーバーが回数を送らないとき agent が上限到達と誤判定することがあった。console-pro のやり直し（`resetModeLocalState`）は会話表示は消すが journey state を初期化しておらず、サーバー側にも回数を対で補う処理がない。

メール／DMと口コミ返信の「1つ前に戻る」、コピー専用セッションを画面入場で捨てる処理は、console-pro にすでにある。この Issue では再実装しない。

## やったこと

- #706 → #707 → #708 のスタックでブラウザ確認をした
- ヒアリングの修正操作で次の2件を確認し、セッション 49・50 の会話ログ（`SHOP_AGENT_CONVERSATION_LOGS`）で原因を特定した
  - 確認カードで修正を選ぶと `hearing_question_count` が 1 戻ったように見える（`ProComposedCheckpointV2Builder::journeyState()` が agent の journey を画面リクエストで上書きしている）
  - 回数 3 到達後、同じ質問が繰り返され下書きに進めない（`withCurrentCheckpointRestoreSnapshot()` が古い checkpoint の journey とヒアリング状態で agent を上書きしている）
- 対応方針を決めた（`journeyState()` を mypl_pro と同じ優先にする；会話が checkpoint より進んでいるターンでは `restore_snapshot` を付けない）
- #706〜#708 のレビュー反映で受け入れ条件を修正した（agent-dev#421 以降の上限メッセージ廃止を反映）

## 残りのやること

- `journeyState()` を mypl_pro と同じく、agent の応答を優先する形にする
- checkpoint の後に会話が進んでいる（`hearingStateBlobForResume()` が snapshot と違う新しいヒアリング状態を返す）ターンでは、`restore_snapshot` を付けずに上位の値で送る。巻き戻し・再開の直後は今までどおり snapshot を付ける
- 「最初からやり直す」の次の送信に、前回の `hearing_question_count` と `material_ledger` が含まれない
- 回数が空のときは、サーバー側で補わずに agent の台帳からの数え直しに任せる（agent-dev#421）。checkpoint や画面の journey に回数があるときは、その値をそのまま送る
- ヒアリング中に、上限メッセージ「ヒアリングの上限に達しました」が表示されない
- 回数が 3 に達して主役の聞き直し質問が出たら、それは 1 回だけで、次の回答で仮の下書きへ進む（同じ質問を繰り返さない）
- 回数が 3 に達した状態から「最初からやり直す」→ 内容をまとめて送ると、前回の回数と材料を送らずに、新しいヒアリングが回数 0 から始まる（聞き直し質問やいきなりの下書きにならない）
- やり直し後やモード開始後も、言い方は残る。会話の途中で初期設定チャットから言い方を変えた場合は、変えたあとの言い方が残る
- メール／DMと口コミ返信の「1つ前に戻る」の現行挙動は変えない
