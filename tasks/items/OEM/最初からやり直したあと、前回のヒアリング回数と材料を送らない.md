## 概要

ニュース作成のヒアリングで「最初からやり直す」を押したあと、次の送信に前回のヒアリング回数と材料が残らないようにする。ヒアリング状態を送るときは、回数の扱いは agent-dev#421 以降の台帳からの数え直しと、checkpoint や画面 journey にある値の送信に合わせる。

メール／DMと口コミ返信の「1つ前に戻る」、コピー専用セッションを画面入場で捨てる処理は、console-pro にすでにある。この Issue では再実装しない。

## やったこと

- #706 → #707 → #708 のスタックでブラウザ確認中、ヒアリングの修正操作で次の2件を特定した（2026-11-02）。確認カードで修正を選ぶと `hearing_question_count` が1戻ったように見える。回数3到達後は同じ主役の聞き直し質問が繰り返され下書きに進めない。セッション49・50の会話ログで body と checkpoint を突合した。
- 原因1：`MyplkunAgentService::withCurrentCheckpointRestoreSnapshot()`（`ChatPayloadBuilder` に同写し）が `restore_snapshot` 付きで journey と `agent_hearing_state_blob` を古い checkpoint で上書きし、質問が続く間は毎ターン同じ古いヒアリング状態が agent に送られていた（事象2）。mypl_pro は `restore_snapshot` を送らない。
- 原因2：`ProComposedCheckpointV2Builder::journeyState()` が画面 journey を `array_replace` で agent 応答に重ね、agent の journey を捨てていた（事象1）。mypl_pro は agent 応答を優先する。
- 対応方針：`journeyState()` を mypl_pro 同様 agent 優先にする。checkpoint より後に会話が進んでいるターンでは `restore_snapshot` を付けず上位の値で送る（2026-11-02）。
- #706〜#708 のレビュー反映で受け入れ条件を修正した（2026-11-04）。回数が空のときはサーバーで0を補わず agent の台帳数え直しに任せ、checkpoint や画面 journey に回数があるときはその値を送る。上限メッセージ「ヒアリングの上限に達しました」は agent-dev#421 以降出ない前提に合わせ、回数3到達時の聞き直し1回とやり直し後の回数0開始を明文化した。言い方はやり直し・モード開始後も残し、会話途中の初期設定チャットでの変更後も残る。

## 残りのやること

- 「最初からやり直す」の次の送信に、前回の `hearing_question_count` と `material_ledger` が含まれない
- 回数が空のときはサーバー側で補わず agent の台帳からの数え直しに任せる。checkpoint や画面 journey に回数があるときはその値をそのまま送る
- ヒアリング中に上限メッセージ「ヒアリングの上限に達しました」が表示されない
- 回数が3に達して主役の聞き直し質問が出たら1回だけとし、次の回答で仮の下書きへ進む（同じ質問を繰り返さない）
- 回数3から「最初からやり直す」→内容をまとめて送ると、前回の回数と材料を送らず回数0から新しいヒアリングが始まる（聞き直し質問やいきなりの下書きにならない）
- やり直し後やモード開始後も言い方は残る。会話途中で初期設定チャットから言い方を変えた場合は変えたあとの言い方が残る
- `journeyState()` を agent 応答優先に直す（原因2）
- checkpoint より後に会話が進んでいるターンでは `restore_snapshot` を付けず送る（原因1）
- メール／DMと口コミ返信の「1つ前に戻る」の現行挙動は変えない
