## 概要

ニュース作成のヒアリングで「最初からやり直す」を押したあと、次の送信に前回のヒアリング回数と材料が残らないようにする。ヒアリング状態を送るときは、回数も必ず対で送る。

メール／DMと口コミ返信の「1つ前に戻る」、コピー専用セッションを画面入場で捨てる処理は console-pro にすでにある。この Issue では再実装しない。

mypl_pro ではやり直し後もブラウザに前回の hearing_question_count と material_ledger が残り、サーバーは回数が空のとき送らず agent が上限到達と誤判定していた。console-pro の resetModeLocalState は journey state を初期化していない。

## やったこと

- #706 → #707 → #708 のスタックでブラウザ確認中、ヒアリング修正操作で2件の不具合を確認した
- 事象1: 確認カードで修正を選ぶと hearing_question_count が1戻ったように見える（次送信では正しい回数）
- 事象2: 回数3到達後、同じヒアリング質問が繰り返され下書きに進めない
- ローカルセッション49・50の会話ログと agent 送信 body・checkpoint を突合して原因を特定した
- 原因1: MyplkunAgentService::withCurrentCheckpointRestoreSnapshot（ChatPayloadBuilder も同様）が restore_snapshot 付きで古い checkpoint の journey/hearing を毎ターン送っていた
- 原因2: ProComposedCheckpointV2Builder::journeyState() が agent 応答より画面 journey を array_replace で優先していた（mypl_pro は agent 優先）

## 残りのやること

- 受け入れ条件: やり直し後の送信に前回の hearing_question_count と material_ledger が含まれない
- 受け入れ条件: やり直し後も user_preference_style は残る
- 受け入れ条件: ヒアリング状態送信時、回数が空なら0を同梱。checkpoint に回数があるときは上書きしない
- 受け入れ条件: 上限表示のあとやり直してまとめ入力すると新しくヒアリングを続けられる（現スタックでは未確認のため修正2本を積む方針）
- 受け入れ条件: メール／DM・口コミ返信の「1つ前に戻る」現行挙動は変えない
- 対応: journeyState() を mypl_pro と同様 agent 応答優先にする（原因2）
- 対応: hearingStateBlobForResume が checkpoint より新しいヒアリング状態を返すターンでは restore_snapshot を付けず上位の値で送る（原因1）。巻き戻し直後は従来どおり snapshot
- テスト: やり直し後 payload・回数0同梱の Vitest/PHPUnit、上限後やり直しの確認
