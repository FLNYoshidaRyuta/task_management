## 概要

ニュース作成のヒアリングで「最初からやり直す」を押したあと、次の送信に前回のヒアリング回数と材料が残らないようにする。ヒアリング状態を送るときは、回数も必ず対で送る。

メール／DMと口コミ返信の「1つ前に戻る」、コピー専用セッションを画面入場で捨てる処理は、console-pro にすでにある。この Issue では再実装しない。

mypl_pro では、やり直し後もブラウザに前回の `hearing_question_count` と `material_ledger` が残っていた。サーバーはヒアリング状態だけを送り、回数が空のときは送らないことがあった。agent 側は回数が無いと上限に達したと扱い、「ヒアリングの上限に達しました」へ誤って落ちていた。本番の会話でも発生している。console-pro のやり直し（`resetModeLocalState`）は、会話表示は消すが journey state を初期化していない。会話画面は `setUserJourneyState` をそのまま渡している。サーバー側の状態組み立てにも、回数を対で補う処理が無い。

対応する mypl_pro の Issue / PR: https://github.com/FutureLinkNetwork/mypl_pro/issues/1169 、関連 agent-dev: https://github.com/FutureLinkNetwork/agent-dev/issues/418 。対照として console-pro にすでにあるもの: 開始案内へ1つ戻る https://github.com/FutureLinkNetwork/mypl_pro/issues/1096 、https://github.com/FutureLinkNetwork/mypl_pro/pull/1105 。コピー専用セッションの廃棄: console-pro の `abandonActiveCopyOnlyTaskSessions` 。

## やったこと

#706 → #707 → #708 のスタックでブラウザ確認をしたところ、ヒアリングの修正操作で次の2つが起きた。

1. 確認カードで「入れたい内容が違う」などの修正を選ぶと、`hearing_question_count` が1戻ったように見える。次の送信では正しい回数になる。
2. 回数が3に達したあとは、回答を送っても「今回の投稿で一番伝えたいことは何ですか？」が繰り返され、下書きに進めない。

ローカル環境のセッション49・50の会話ログ（`SHOP_AGENT_CONVERSATION_LOGS`）で、agent に送った body と保存された checkpoint を突き合わせて確認した。

原因1（事象2）: `MyplkunAgentService::withCurrentCheckpointRestoreSnapshot()`（`ChatPayloadBuilder` にも同じ写し）が、`restore_snapshot` を付けたうえで `user_journey_state` と `current_state.agent_hearing_state_blob` を snapshot の値で上書きしている。checkpoint はヒアリング質問を返したターンでは保存されないため、質問が続く間は毎ターン同じ古い journey とヒアリング状態が agent に送られる。セッション49・回数3到達後の5ターンでは、agent は毎ターン `subject_recovery_spent=true` のヒアリング状態を保存しているが、サーバーは5回とも同じ checkpoint の古いヒアリング状態（`subject_recovery_spent=false`）を送っていた。`hearingStateBlobForResume()` は checkpoint より後に保存されたヒアリング状態を拾う作り（#478）だが、この経路は素通りしている。mypl_pro は agent に `restore_snapshot` を送らず、上位の値で動いている。

原因2（事象1）: `ProComposedCheckpointV2Builder::journeyState()` が、agent の応答の journey に画面がリクエストで送った journey を `array_replace` で重ねており、画面の journey はすべてのキーを持つため agent の応答はまるごと捨てられる。セッション50・seq 18 では、確認カードの後の checkpoint の journey は1つ前のヒアリング質問のターン（seq 11）で agent が返した journey と完全に一致し、そのターン（seq 17）の応答とは一致しなかった。mypl_pro の同じ関数は agent の応答の journey を常に優先する。

対応方針: 原因2は `journeyState()` を mypl_pro と同じく agent の応答を優先する形にする。原因1は checkpoint の後に会話が進んでいる（`hearingStateBlobForResume()` が snapshot と違う新しいヒアリング状態を返す）ターンでは `restore_snapshot` を付けずに上位の値で送る（mypl_pro と同じ）。巻き戻し・再開の直後（checkpoint が最新）は今までどおり snapshot を付ける。

## 残りのやること

- 「最初からやり直す」の次の送信に、前回の `hearing_question_count` と `material_ledger` が含まれない
- やり直し後も、店舗の言い方設定（`user_preference_style`）は残る
- ヒアリング状態を送るターンでは、回数が空なら 0 を付けて対で送る。checkpoint に回数があるときは上書きしない
- 上限表示のあとにやり直してまとめ入力すると、新しくヒアリングを続けられる
- メール／DMと口コミ返信の「1つ前に戻る」の現行挙動は変えない

両方直しても残ること: ヒアリング質問が続く間は checkpoint が保存されないため回数が進まない。mypl_pro も journey は checkpoint のものを最優先にしているのでコード上は同じ（mypl_pro の実ログでは未確認）。上限判定が遅れることはあるが、ループにはならない。

#673 の受け入れ条件「上限表示のあとにやり直してまとめ入力すると、新しくヒアリングを続けられる」をこのままでは確認できないため、#706 → #707 → #708 と同じスタックの上に上記2原因の修正を2本積む。

改修前の再現手順: ニュース作成でヒアリングを数回進める → 「最初からやり直す」 → 新しい内容を送る → 送信内容に前回の回数と材料が残り、上限到達として扱われることがある。

テスト手順: やり直し後の送信 payload に前回の回数と材料が無い Vitest。ヒアリング状態だけがあり回数が空のとき、サーバーが 0 を同梱する PHPUnit。上限表示のあと、やり直してまとめ入力できることを確認する。
